# 데이터베이스 기초 개념

- database : 전자적으로 저장되고 사용되는 관련있는 데이터들의 조직화된 집합
	- DB의 구조 : 데이터 유형, 데이터 관계, 제약 사항
- DBMS(database management systems) : 사용자에게 DB를 정의하고 만들고 관리하는 기능을 제공하는 소프트웨어 시스템
	- metadata(=catalog) : database를 정의하거나 기술하는 data
		- metadata 또한 DBMS를 통해 저장 및 관리된다
- database system(approx. database) : database + DBMS + 연관된 applications
- data models : DB의 구조를 기술하는데 사용될 수 있는 개념들의 집합
	- data models은 DB 구조를 추상화해서 표현하는 데 사용하는 수단과 DB를 읽고 쓰기 위한 기본적인 operations을 포함
	- 종류
		- conceptual data models(=high-level data models) : 일반 사용사도 이해할 수 있는 가장 고수준의 추상화가 된 모델로 비즈니스 요구 사항을 추상화하여 기술할 때 사용
			- e.g. Entity-relationship model(ER model)
			- diagram을 사용해서 누구나 이해할 수 있게 표현
		- logical data models(=representational data models) : 이해하기 어렵지 않으면서 데이터가 실제 컴퓨터에 저장될 때와 크게 다르지 않게 DB를 구조화할 수 있는 개념을 제공
			- e.g. relational data model, object data model, object-relational data model
			- 특정 DBMS나 storage에 종속되지 않는 수준에서 DB를 구조화할 수 있게 표현
		- physical data models(=low-level data models) : 컴퓨터에 데이터가 실제 저장되는 형태를 기술할 수 있는 수단을 제공
- database schema : data model을 바탕으로 DB의 구조를 기술한 것
- database state(=snapshot) : 특정 시점에서 database에 있는 데이터
- database system을 구축하는 architecture
	- three-schema architecture
		- 각 level을 독립시켜서 하위 level의 변화가 상위 level에 영향을 주지 않기 위함 (mapping만 바꿔주면 됨)
		- 3개의 level로 구분하며 각 level마다 schema가 정의되어 있음
			- external level(=view level)의 external schema(=user views) : logical data model을 통해 표현하며 유저마다 필요한 데이터만 표현될 수 있도록 유저 별로 정의될 수 있음
			- conceptual level의 conceptual schema : internal schema를 추상화한 schema로 전체 DB에 대한 구조를 기술하되 물리적인 저장 구조는 숨김
			- internal level의 internal schema : physical data model을 통해서 표현
- database language
	- data definition language (DDL) : conceptual schema를 정의하기 위해 사용되는 언어이지만 internal schema, external schema까지 정의할 수 있는 경우도 있음
	- storage definition language (SDL) : internal schema를 정의하기 위한 언어이지만 요즘 RDBMS에서는 SDL이 거의 없고 파라미터 설정으로 대체됨
	- view definition language (VDL) : external schema를 정의하기 위한 언어이지만 대부분의 DBMS에서는 DDL이 VDL 역할까지 수행함
	- data manipulation language (DML) : database에 있는 data를 활용하기 위한 언어
	- 요즘 DBMS는 DDL, SDL, VDL이 따로 있지 않고 통합된 언어로 존재 e.g. SQL

# Relational Data Model

- relation(table) : 집합들의 cartesian product의 부분집합으로 tuple(=row)로 구성됨
	- e.g.
		- binary relation : 두 domain(집합)의 cartesian product($\times$)의 부분 집합(tuple의 집합)
		- n-ary relation : n개 domain의 cartesian product의 부분 집합
	- domain 마다 attribute(=column)를 갖기 때문에 동일한 domain이 하나의 relation에 여러개 포함될 수 있음
	- relation schema : relation 이름과 attributes 리스트로 표기되며 attributes와 관련된 constraints도 포함함
		- e.g. STUDENT(sid, name, grade)
		- degree of a relation : relation schema에서 attribute의 수 e.g. 3
	- relation state(approx. relation) : 임의 시점에서 tuple의 집합
	- 특징
		- tuple을 식별하기 위해서 attributes의 부분 집합을 key로 설정한다
			- super key : tuple을 unique하게 식별할 수 있는 attributes set
			- candidate key(=minimal super key) : 하나의 attribute만 제거해도 unique하게 식별할 수 없는 super key
				- primary key(=PK) : candidate key 중에 tuple 식별에 사용하기로 선택한 key로 underline을 해서 표시
				- unique key(=alternate key) : primary key가 아닌 candidate key
			- foreign key : 다른 relation의 PK를 참조하는 key
		- cf. prime attribute : 임의의 candidate key에 속하는 attribute
		- relation에서 tuple의 순서는 중요하지 않다
		- 하나의 tuple에서 attribute의 순서는 중요하지 않다
		- attribute는 atomic해야 한다 (더 이상 나눌 수 없어야 한다)
			- composite attribute나 multivalued attribute는 허용안됨
				- composite attribute e.g. 서울시 성북구 화랑로
				- multivalued attribute e.g. 컴공, 생물
- relational database : relational data model에 기반하여 구조화된 database
	- 여러 개의 relations으로 구성됨
	- relational database schema : relation schemas set + integrity constraints set
- NULL : 값이 존재하지 않거나 값은 존재하지만 그 값이 무엇인지 알지 못하는 경우나 해당 사항과 관련이 없을 때 사용
- constraints : DB의 relations이 지켜야 하는 제약 사항
	- implicit constraints : relational data model 자체가 가지는 constraints
		- 중복된 tuple을 가질 수 없다
		- 동일한 attribute name을 가질 수 없다
	- schema-based constraints(=explicit constraints) : DDL을 통해 schema에 명시할 수 있는 constraints
		- domain constraints : attribute의 value는 해당 attribute의 domain에 속한 value여야 한다
		- key constraints : super key는 중복되는 value를 가질 수 없다
		- NULL value constraint : attribute이 NOT NULL로 명시됐다면 NULL을 value로 가질 수 없다
		- entity integrity constraint : primary key는 value에 NULL을 가질 수 없다
		- referential integrity constraint : PK와 FK는 domain이 같아야 하고 FK는 PK에 없는 value를 가질 수 없다 (NULL은 허용 가능)

# SQL 완전 정복

- SQL(Structured Query Language) : RDBMS의 표준 언어
	- SQL에서 relation은 중복된 tuple을 허용하는 multiset(=bag)임
	- RDBMS 마다 제공되는 SQL 스펙이 조금씩 다를 수 있음
		- e.g. MySQL에서는 DATABASE와 SCHEMA가 동일한 의미로 사용되지만 postgreSQL에서는 SCHEMA가 DATABASE의 namespace를 의미 (DATABASE 안에 SCHEMA가 정의되고 그 안에 TABLE이 정의)
- boolean operation : SQL은 chained comparison(e.g. a <= x <= b)이 안되서 따로 따로 써줘야 함
	- = : ==
	- <> : !=
- bitwise operation : &, |
- condition
	- 여러 조건의 conditions은 AND나 OR로 묶어주면 된다
	- 여러 값 동시에 비교 : `year IN (2001, 2002)` or `year IN (subquery)` or `year NOT IN (2001, 2002)`
	- selection condition : 하나의 테이블 내에서 선택하는 조건
	- join condition : 서로 다른 table끼리 비교하는 조건
		- 2개 이상의 table이 포함되면 \*로 모든 attribute 가져올 때 각 table의 column이 모두 붙어서 나오게 됨
	- NULL을 비교할 때는 `id = NULL` 말고 `id IS NULL`로 비교해야 됨
		- 반대의 경우는 `id IS NOT NULL`
		- three-valued logic : 비교/논리 연산의 결과는 TRUE, FALSE, UNKNOWN을 갖는다
			- NULL은 어떤 비교/논리 연산을 하든지 결과가 UNKNOWN이 됨
			- WHERE 절은 condition의 결과가 TRUE인 tuple만 선택됨 e.g. NOT IN의 결과가 UNKNOWN인 경우 결과가 나오지 않음 => IS NOT NULL로 NULL인 경우를 제외해줘야 됨
	- BETWEEN : 경계를 포함하여 사이에 있는지 확인 e.g. `WHERE date BETWEEN '2001-01-01' AND '2011-01-01'`
- JOIN
	- implicit join : FROM 절에서 관련 table을 나열하고 WHERE 절에서 join condition을 명시하는 방식
	- explicit join : FROM 절에 JOIN 키워드와 함께 joined table을 명시하는 방식으로 ON 뒤에 join condition을 명시해주면 된다 e.g. `FROM employee AS E JOIN department AS D ON E.dept_id = D.id`
		- inner join : 그냥 JOIN이 INNER JOIN을 축약한 것임. join condition 결과가 true인 tuple들로만 result table을 만듦
		- outer join : join condition을 만족하지 않는 tuple들도 result table에 포함하는 join. OUTER는 생략 가능
			- `FROM table1 LEFT OUTER JOIN table2 ON cond` : table1은 무조건 포함
			- `FROM table1 RIGHT OUTER JOIN table2 ON cond` : table2는 무조건 포함
			- `FROM table1 FULL OUTER JOIN table2 ON cond` : table1, table2 모두 무조건 포함. MySQL에는 FULL JOIN이 없음
		- natural join : 이름이 동일한 모든 attribute pair에 대해서 equi join을 수행
			- `FROM table1 NATURAL JOIN table2`
			- `FROM table1 NATURAL LEFT JOIN table2`
			- `FROM table1 NATURAL RIGHT JOIN table2`
			- `FROM table1 NATURAL FULL JOIN table2`
		- cross join : cartesian product를 result table로 반환. MySQL에서는 CROSS JOIN이랑 INNER JOIN이 동일하게 작동함
			- `FROM table1, table2`
			- `FROM table1 CROSS JOIN table2`
		- 한 번에 여러 JOIN을 동시에 적용할 수도 있음 e.g. `FROM works_on W JOIN employee E ON W.empl_id = E.id LEFT JOIN department D ON E.dept_id = D.id`
	- equi join : join condition에 equality comparator(=)를 사용한 join
		- equi join에서 비교하는 attribute name이 동일한 경우 result table에 동일한 이름의 attribute가 포함되는데 이런 경우는 그냥 USING을 사용하면 더 간편하면서 attribute가 한 번만 표시되게 비교할 수 있다. e.g. `FROM table1 JOIN table2 USING (attribute(s));`
	- self join : 자기 자신에게 join하는 것 e.g. `FROM DATA AS DL JOIN DATA AS DR ON cond`
- UNION : 중복을 제거하며 왼쪽과 오른쪽 결과를 합침
	- UNION ALL : 중복을 제거하지 않고 왼쪽과 오른쪽 결과를 합침
- 명령어
	- `CREATE DATABASE db_name;` : DB 만드는 명령어
	- `DROP DATABASE db_name` : DB 삭제하는 명령어
	- `USE db_name;` : 현재 사용할 DB 선택하는 명령어
	- `SELECT database();` :  현재 선택한 DB 보는 명령어
	- `CREATE TABLE table_name (id INT PRIMARY KEY, name VARCHAR(20), NOT NULL UNIQUE, leader_id INT);` : table을 만드는 명령어
	- `ALTER TABLE table_name COMM;` :  table을 변경하는 명령어
	- `DROP TABLE table_name;` : table을 제거하는 명령어
	- `INSERT INTO table_name VALUES tuple;` : table에 row를 넣는 명령어
		- tuple 데이터 순서를 임의로 지정해서 삽입도 가능 e.g. INSERT INTO employee (name, position, id) VALUES ('seokzoo', 'DEV', 3);
		- 한 번에 여러 row 삽입도 가능 e.g. INSERT INTO table_name VALUES tuple1, tuple2, tuple3;
	- `UPDATE table_name SET attr_name1 = value1 WHERE cond` : row의 value를 업데이트하는 명령어
		- 여러 table과 연관되어 update하고 싶으면 `UPDATE table_name1, table_name2 ...` 이런 식으로 테이블을 다 적어주면 된다
		- 여러 attribute를 동시에 업데이트하고 싶으면 `attr1 = value1, attr2 = value2` 처럼 써주면 된다
		- 특정 table의 특정 attribute를 지정하고 싶으면 `table_name.attribute_name`으로 써주면 된다
		- WHERE은 optional임 
	- `DELETE FROM table_name WHERE cond` : 특정 rows를 제거하는 명령어
	- `SELECT attributes FROM table_name WHERE cond;` : 데이터 조회하는 명령어
		- AS : AS는 생략도 가능함
			- `FROM table_name AS alias` : table을 가져올 때 별칭으로 가져올 수 있음
			- `SELECT attribute AS alias` : attribute도 가져올 때 별칭으로 가져올 수 있음
		- DISTINCT : `SELECT DISTINCT attributes FROM table_name` : 중복된 tuple을 제거하는 명령어
			- 만약에 유일한 것들의 개수를 샌다면 `SELECT COUNT(DISTINCT name)`
		- LIKE
			- WHERE name LIKE \'N%\' or \'%N\' : 이름이 N으로 시작하거나 끝나는 row 가져오기
			- WHERE name LIKE \'%NG%\' : 이름에 NG가 들어가는 row 가져오기
			- WHERE name LIKE \'J___\' : 이름이 J로 시작하고 4글자인 row 가져오기
			- \% 나 \_ 문자 자체를 사용하고 싶으면 앞에 \\를 붙여주면 됨
		- aggregate function : NULL을 제외한 여러 tuple의 정보를 요약해서 하나의 값으로 추출하는 함수
			- MAX, MIN : attribute에서 가장 크거나 작은 value를 가져옴 e.g. `SELECT max(salary) FROM employee`
			- COUNT : 개수 반환 e.g. `SELECT COUNT(*) FROM table`
			- SUM
			- AVG : 평균 반환 e.g. `AVG(salary)`
		- PARTITION BY : GROUP BY를 사용하지 않고 GROUP 별로 aggregate function을 사용할 수 있음 `SUM(salary) OVER (PARTITION BY job)`
		- ROUND : 소수점 반올림해서 반환 e.g. `ROUND(AVG(salary), 1)` - 소수점 한 자리 남기고 반올림
		- IFNULL : NULL일 때 다른 값으로 반환 e.g. `IFNULL(NO, 'NONE')`
		- IF : 조건문 e.g. `IF(cond, TRUE, FALSE)`
		- CONCAT : 다른 자료형끼리도 가능함 e.g. `CONCAT(MAX(LENGTH), 'cm')`
		- ORDER BY : 정렬해서 가져올 수 있음. default는 ASC라서 생략 가능
			- e.g. `SELECT * FROM employee ORDER BY dept_id, salary DESC`
		- GROUP BY : attribute(s)의 같은 value끼리 묶어서 결과를 반환
			- grouping attribute(s)에 NULL이 포함되면 NULL 값을 갖는 tuple끼리 묶임
			- e.g. `SELECT dept, CONUT(*), MAX(salary) FROM table GROUP BY dept;`
			- HAVING : aggregate function을 사용해서 결과를 필터링하고 싶을 때 사용 가능(GROUP BY 뒤에 와야 함) e.g. `SELECT class, AVG(score) FROM table GROUP BY class HAVING AVG(score) > 80;`
		- LIMIT : 앞의 n개 데이터만 가져옴 e.g. `LIMIT 2`
- subquery(=nested query, inner query) : outer query(=main query)에 포함된 query
	- ( ) 안에 작성해주면 됨 e.g. `SELECT id FROM employee WHERE (dept, sex) = (SELECT dept, sex FROM employee WHERE id = 3);`
	- subquery로 가상의 테이블을 만들어 낼 수 있음 e.g. `SELECT name FROM employee, (SELECT id FROM table WHERE dept = 'dev') AS ID_E WHERE ID_E.id = id;`
	- EXISTS : subquery 결과가 존재하면 true를 반환 e.g. `SELECT P.id, P.name FROM project P WHERE EXISTS (SELECT * FROM works_on W WHERE W.proj_id = P.id AND W.empl_id IN (7, 12);`
		- EXISTS는 IN으로 바꿔서 작성할 수 있지만 IN 같은 경우는 결과가 UNKNOWN이면 아무것도 출력되지 않는다는 점에 유의해야 됨 e.g. `id IN (SELECT proj_id ...)`
		- NOT EXISTS도 가능함
	- ANY : subquery가 반환한 결과 중에 단 하나라도 이전 비교 연산자 결과가 참일 경우 true를 반환 e.g. `E.salary < ANY (SELECT salary FROM employee)`
		- SOME도 ANY와 같은 역할을 함
	- ALL : subquery가 반환한 모든 결과에 대해서 이전 비교 연산자 결과가 모두 참일 경우 true를 반환 e.g. `W.proj_id <> ALL (SELECT proj_id FROM works_on)`
	- correlated query : subquery가 바깥쪽 query의 attribute를 참조하는 경우
- CTE(Common Table Expressions)
	- WITH : subquery와 유사한데 이름을 붙일 수 있음 e.g. `WITH TEMP AS (subquery) main_query`
	- WITH RECURSIVE : 재귀를 사용해서 
- 자료형
	- 숫자
		- INT
			- TINYINT(1byte)
			- SMALLINT(2byte)
			- MEDIUMINT(3byte)
			- INT or INTEGER(4byte)
			- BIGINT(8byte)
		- floating-point
			- FLOAT(4byte)
			- DOUBLE or DOUBLE PRECISION(8byte)
		- fixed-point
			- DECIMAL or NUMERIC (precision, scale)
				- e.g. DECIMAL(5, 2) => \[-999.99 ~ 999.99\]
				- 표준 SQL에서는 DECIMAL은 소수점 범위를 벗어나도 저장하는데 MySQL은 아님
	- 문자열
		- 고정 크기 문자열 - CHAR(n) : 최대 길이보다 적으면 space로 채움
		- 가변 크기 문자열 - VARCHAR(n) : 길이만큼 저장
		- 사이즈가 큰 문자열 - TINYTEXT, TEXT, MEDIUMTEXT, LONGTEXT
	- 날짜와 시간
		- 날짜 DATE : YYYY-MM-DD를 저장
		- 시간 TIME : hh:mm:ss나 hhh:mm:ss를 저장
		- 날짜와 시간 DATETIME or TIMESTAMP : YYYY-MM-DD hh:mm:ss를 저장하는데 timestamp는 time-zone을 UTC 기준으로 저장
	- byte-string 저장 - BINARY, VARBINARY, BLOB type
	- boolean : MySQL은 없어서 그냥 TINYINT로 대체해서 사용
	- 위치 - GEOMETRY
	- JSON
- key constraints
	- 종류
		- PRIMARY KEY : 여러 attribute를 PK로 적용하려면 `CREATE TABLE table_name (id INT, name VARCHAR(20), NOT NULL UNIQUE, leader_id INT, PRIMARY KEY(id, leader_id));`
		- UNIQUE : 해당 attribute가 중복된 값을 갖지 못하게 하는 것으로 NULL 중복 허용은 RDBMS에 따라 다름
		- NOT NULL
		- DEFAULT value : 해당 attribute의 default 값을 value로 지정
		- CHECK (condition) : condition이 만족하도록 지정
			- 하나의 attribute으로 구성되는 경우 e.g. age INT CHECK (age >= 20)
			- 둘 이상의 attribute으로 구성되는 경우 따로 써줘야 함 e.g. CHECK (start_date < end_date)
		- FOREIGN KEY (attr_name) REFERENCES table_name(attribute_name) on delete reference_option on update reference_option
			- reference options
				- CASCADE : 참조값의 삭제/변경을 그대로 반영
				- SET NULL : 삭제/변경되면 NULL로 변경
				- RESTRICT : 삭제/변경되는 것을 금지
				- NO ACTION : MySQL에서는 RESTRICT랑 동일한데 표준 스펙에서는 한 트랜젝션 종료 전까지는 달라도 됨을 의미
				- SET DEFAULT : 삭제/변경되면 default value로 변경
	- CONSTRAINT constraint_name : key constraints에 이름을 붙여줄 수 있음
		- e.g. age INT CONSTRAINT age_over_20 CHECK (age > 20)
- delimiter : query가 끝이 났다는 것을 알려주는 단어로 `delimiter $$`로 바꿔줄 수 있음
- stored function : 사용자 정의 함수
	- function은 return이 필수임
	- SQL statement 내부에서 사용 가능

``` mysql
SHOW FUNCTION STATUS where DB = 'db_name';
SHOW CREATE FUNCTION func_name;

delimiter $$
CREATE FUNCTION db_name.func_name()
RETURNS INT
BEGIN
	DECLARE var1 int;
	SELECT COUNT(attr) into var1 FROM table_name;
	SELECT COUNT(attr) into @var2 FROM table_name;
	IF var1 IS NULL THEN SET var1 = 0;
	ELSEIF var1 < 10 THEN SET var1 = 1;
	ELSE SET var1 = 10;
	END IF;
	RETURN var1 + @var2;
END
$$
delimiter ;

DROP FUNCTION func_name;
```

- stored procedure : 사용자 정의 procedure
	- parameter 앞에 IN(이게 default임)이면 read만 되고 OUT이면 write만 되고 INOUT이면 둘 다 가능
	- 따로 return 같은 키워드 없이 select 쓰면 결과 반환이 되고 꼭 무언가 반환할 필요가 없음
	- SQL statement 내부에서 사용 불가능
	- 장점 : 웹서버와 DB가 데이터 주고 받을 때 network traffic이 발생하는데 stored procedure를 통해서 DB에서 처리하게 하면 network traffic이 감소함

``` MySQL
delimiter $$
CREATE PROCEDURE procedure_name(IN a int, INOUT b int, OUT result int)
BEGIN
	SET result = a * b;
	SELECT * FROM table_name;
END
$$
delimiter ;

CALL procedure_name(5, 7, @result);
SELECT @result;
```

- Trigger : DB에서 insert, update, delete가 발생했을 때 자동적으로 실행되는 procedure
	- OR로 event를 동시에 감지하는 것은 MySQL에서는 지원안함
	- BEFORE는 event 발생 전 작동, AFTER는 발생 이후에 작동
	- OLD는 event 발생 전 tuple을 나타내고 NEW는 event 발생 후 tuple을 나타냄
	- FOR EACH ROW면 영향 받은 row 개수만큼 실행이 되고 FOR EACH STATEMENT로 하면 statement 단위로 실행됨
	- WHEN은 어떤 조건을 만족할 때만 실행되도록 하는 것임 e.g. `WHEN (NEW.nickname IS DISTINCT FROM OLD.nickname)`

``` MySQL
delimiter $$
```

# 트랜잭션과 병행제어

- transaction : 단일한 논리적 작업 단위
	- 여러 SQL문을 transaction으로 묶어서 나뉠 수 없게 만든 것 -> SQL문 중 일부만 성공해서 DB에 반영될 수 없음
	- COMMIT : 지금까지 작업 상황을 DB에 영구적으로 반영하라는 명령어
	- ROLLBACK : 지금까지 작업을 모두 취소하고 transaction 이전으로 돌리는 명령어
	- SQL문이 성공하면 자동으로 COMMIT해주는 기능. 기본으로 enabled되어 있음.
	- START TRANSACTION을 하게 되면 autocommit이 자동으로 disabled됨

``` MySQL
SELECT @@AUTOCOMMIT;
SET autocommit=0;

START TRANSACTION;
UPDATE account SET balance = balance - 20 WHERE id = 1;
UPDATE account SET balance = balance + 20 WHERE id = 2;
COMMIT;

START TRANSACTION;
UPDATE account SET balance = balance - 20 WHERE id = 1;
ROLLBACK;

```

- ACID : transaction의 성질
	- Atomicity : transaction은 내부의 SQL이 모두 성공하거나 실패해야됨 (ALL or NOTHING)
	- Consistency : DB의 rule이 consistent하게 유지되어야 한다는 뜻
		- trigger나 constraints를 통해 작업이 DB에 정의된 rules을 위배했다면 rollback해야 됨
	- Isolation : 여러 transaction이 동시에 실행될 때도 개별적으로 실행되어 서로 영향을 주지 않아야함
		- concurrency control의 주요 목표가 isolation임
		- DBMS에서는 여러 level의 isolation을 제공함
	- Durability : commit된 transaction은 DB에 영구적으로 반영되어야 함 (DB system에 문제가 발생해도 commit이 끝난 transaction은 DB에 반영되어 있어야 함)
- Schedule : 여러 transaction이 동시에 수행될 때 각 transaction의 operations들의 실행 순서
	- 각 transaction 내의 operations들의 순서는 바뀌지 않음
	- serial schedule : 각 transaction 들이 곂치지 않고 한 번에 하나씩 실행되는 schedule. 성능이 느려서 현실적으로 사용하기 어려운 방법.
	- nonserial schedule : transaction들이 곂쳐서 실행되는 schedule. 동시성이 높아져서 같은 시간 동안 더 많은 transaction들을 처리할 수 있음.
- conflict의 조건 (for operations)
	- 각 operation이 서로 다른 transaction에 속할 것
	- 같은 데이터에 접근할 것
	- 최소 하나는 write operation일 것
- conflict equivalent의 조건 (for schedules) : 두 schedule이 같은 transaction을 가지면서 모든 conflicting operations의 순서가 동일한 경우
- conflict serializable (for a schedule) : serial schedule과 conflict equivalent한 경우
	- 어떤 schedule이 conflict serializable하면 conflict serializability 속성을 갖는다고 함
- unrecoverable schedule : $T_j$가 $T_i$가 write한 값을 읽었는데 i보다 j가 먼저 commit해버리는 경우 e.g. tr1 w1(h) tr2 r2(h) w2(h) cm2 rb1(h)
		- DBMS는 unrecoverable schedule을 허용하면 안됨
	- recoverable schedule : schedule 내의 모든 transaction에 대해서, 자신이 읽은 데이터를 write한 transaction이 먼저 commit/rollback하기 전까지는 commit하지 않는 경우 ($c_i \lt c_j$)e.g. tr1 w1(h) tr2 r2(h) rb1(h) w2(h) 
		- recoverable schedule은 rollback을 통해서 복구가 가능함
		- cascading rollback : 하나의 transaction이 rollback 했을 때, 의존성이 있는 다른 transaction도 rollback하는 경우. 처리하는데 비용이 많이 발생함
		- cascadeless schedule(=avoid cascading rollback) : schedule 내 어떤 transaction도 commit되지 않은 transaction에서 write한 내용을 읽지 않는 경우 ($c_i \lt r_j(X)$)
			- cascadeless schedule이어도 tr1 w1(h) tr2 w2(h) rb1(h)을 하면 w2 결과가 사라지는 문제점이 있음
				- strict schedule : schedule 내 어떤 transaction도 commit되지 않은 transaction이 write한 내용을 읽거나 쓰지 않는 경우 ($w_i(X) < (c_i\ \text{or}\ a_i) < (r_j(X)\ \text{or}\ w_j(X))$)
- isolation이 안될 때 일어날 수 있는 현상
	- dirty read : commit되지 않은 write을 읽은 경우
	- non-repeatable read(=fuzzy read) : 하나의 transaction 내에서 같은 값을 읽을 때 값이 달라지는 경우
	- phantom read : 어떤 조건의 데이터를 여러 번 select 했을 때, 그 사이에 다른 데이터의 조건이 바뀌어서 select 결과가 달라지는 경우 (즉, 없던 데이터가 생기는 경우)
	- dirty write : commit되지 않은 데이터에 write를 하는 경우
	- lost update : 업데이트가 업데이트를 덮어 쓰는 현상
	- read skew : inconsistent한 데이터 읽기가 발생한 경우 (x가 y에게 40 때어주는 transaction 1과 x와 y를 읽는 transaction 2이 발생한다고 할 때, transaction 2가 처리되는 과정에서 transaction 1이 수행되는 경우)
	- write skew : inconsistent한 데이터 쓰기가 발생한 경우 (초기 상태에서 어떤 조건을 만족하는 두 데이터에 대해서 개별 트랜잭션을 수행했을 때는 문제가 없지만, 동시에 실행됐을 때 둘 다 초기 상태를 read하여 문제가 발생하는 경우)
- 표준 SQL 문서의 isolation level
	- 모든 isolation level에서 dirty write은 허용되지 않음
	- read uncommitted : read 시점을 기준으로 commit 여부와 상관없이 데이터를 읽음 (dirty read, non-repeatable read, phantom read를 모두 허용)
	- read committed : read 시점을 기준으로 직전에 commit된 데이터를 읽음 (non-repeatable read, phantom read를 허용)
	- repeatable read : tx 시작 시간 기준으로 직전에 commit된 데이터를 읽음 (phantom read만 허용)
	- serializable : 모두 허용하지 않으며 이상한 현상 자체가 발생하지 않음
- Concurrency control : 어떤 schedule을 serializable하고 recoverable하게 만들어줌
	- lock : write_lock과 read_lock, unlock을 통해서 lock을 가진 transaction만 권한을 주는 방법
		- write-lock (=exclusive lock) : read, write를 할 권한이 생기며 다른 tx이 같은 데이터를 read, write하는 것을 허용하지 않는다
		- read-lock (=shared lock) : read할 권한이 생기며 다른 tx가 같은 데이터를 read하는 것은 허용한다 
		- lock을 써도 발생하는 이상한 현상들
			- x와 y를 더해서 x에 저장하는 tx와 x와 y를 더해서 y에 저장하는 tx 상황을 lock을 사용해 구현하면 non-serializable한 상황이 나올 수 있음 => 해결 방법 : 2PL protocol(read_lock 또는 write_lock을 unlock하기 전에 write_lock을 얻으면 됨)
		- 2PL protocol(=two-phase locking protocol) : tx에서 모든 locking operation을 최초의 unlock operation보다 먼저 수행되도록 하는 것 (최초의 unlock 후에는 새로운 lock을 얻지 않는다)
			- phase
				- expanding phase : lock을 취득하기만 하는 phase
				- shrinking phase : unlock만 하는 phase
			- 2PL protocol에서는 deadlock이 발생할 수 있음
			- 종류
				- conservative 2PL : 모든 lock을 취득한 다음 transaction을 시작하는 방법으로 deadlock-free임
				- strict 2PL (=S2PL) : write-lock을 commit 또는 rollback 이후에 unlock하는 방법으로 strict schedule을 보장함
				- strong strict 2PL (=SS2PL) : read-lock과 write-lock 모두 commit 또는 rollback 이후에 unlock하는 방법으로 strict schedule을 보장함
			- 2PL은 read lock만 동시에 사용하는 것이 가능하기 때문에 성능이 낮음
	- MVCC(multi version concurrency control)
		- snapshot isolation : 한 transaction 내의 작업을 transaction 시작 시점의 snapshot에 적용하고 commit할 때 db에 반영하는 방법 (conflict가 발생하면 먼저 commit된 내용만 반영하고 뒤에 commit은 abort시킴)
		- 구현할 때 write lock을 사용할 수도 있고 안 할 수도 있음
			- MVCC에서는 snapshot isolation을 사용하기 때문에 어떤 tx가 write lock을 얻어도 다른 tx에서 원본 state를 기준으로 read를 할 수 있음
		- isolation level에 따라서 read commited일 수도 있고 repeatable read, serializable 일 수 있고 tx 별로 다른 isolation level을 적용할 수도 있음
		- read와 write가 서로를 block하지 않기 때문에 lock-based concurrency control 보다 성능이 나음

# 함수 종속성과 정규화

- functional dependency : 한 테이블에 있는 두 개의 attribute(s) 집합 사이의 constraint
	- $X\rightarrow Y$ : x 집합에 의해 y집합이 유일하게 결정될 때 x가 y를 함수적으로 결정한다(functionally determine) 또는 y가 x에 함수적으로 의존한다(functionally dependent)라고 함 e.g. $\{\text{sid}, \text{class\_id}\}\rightarrow\{\text{grade}\}$, $\{\}\rightarrow\{\text{company}\}$(attribute의 값이 항상 동일한 경우)
	- 종류
		- trivial functional dependency : $X\rightarrow Y$ 일때 Y가 X의 부분집합일 때, $X\rightarrow Y$는 trivial FD
		- non-trivial function dependency : trivial FD가 아닌 FD
			- completely non-trivial FD : X와 Y의 교집합이 공집합인 경우
		- partial functional dependency : X의 어떤 진부분집합(proper subset)이 Y를 함수적으로 결정할 수 있는 경우
		- full functional dependency : X의 어떤 진부분집합도 Y를 함수적으로 결정할 수 없는 경우
	- Armstrong's axioms
	- Closure
	- minimal cover
- DB normalization : 데이터 중복, 각종 anomaly를 최소화하기 위해서 일련의 normal forms(NF)에 따라 RDB를 구성하는 과정
	- DB 정규화 과정 : 순차적으로 진행되며 앞 단계를 만족해야 다음 단계 진행이 가능하다
		- 1NF : attribute의 value는 나눠질 수 없는 단일한 값이어야 한다(atomic)
		- 2NF : 모든 non-prime attribute는 모든 candidate key에 대해서 fully FD 해야 한다
			- 공집합에 함수적으로 의존하는 경우를 제외하면 candidate key가 composite key가 아니라면 2NF는 자동으로 만족한다
		- 3NF(정규화의 최소 기준) : 모든 non-prime attribute는 어떤 candidate key에 대해서도 transitively dependent 해서는 안된다 (non-prime attribute와 non-prime attribute 사이에는 FD가 존재하면 안된다)
			- transitive FD : Y와 Z가 어떤 candidate key의 부분집합도 아니면서 $X\rightarrow Y$, $Y\rightarrow Z$ 일때 $X\rightarrow Z$를 transitive FD라고 함
		- BCNF : 모든 non-trivial FD $X\rightarrow Y$에서 X는 super key여야 한다
		- 4NF
		- 5NF
		- 6NF
	- denormalization : 성능을 위해서 굳이 normalization하지 않고 table을 합치는 것

# 인덱스와 파일 구조

- full scan(=table scan) : 모든 tuple을 linear search로 탐색
- Index
	- 사용 이유 : 빠른 조회, 빠르게 정렬, 빠른 그룹핑
	- multicolumn index(=composite index) : 여러 attribute를 동시에 index로 사용하는 경우
	- B-tree 기반의 index 동작 원리 : index와 ptr로 구성된 테이블을 만든 다음, index를 기준으로 정렬 시켜서 index에 접근할 때 binary search로 탐색
		- B-Tree : BST를 확장하여 일반화한 tree
			- M : 각 노드의 최대 자녀 노드 수 (M차 B-Tree라고 부름)
				- 각 노드의 최대 key 수 = M-1
				- 각 노드의 최소 자녀 노드 수(root, leaf 제외) = $\operatorname*{ceil}(M/2)$
					- root의 경우 leaf가 아니라면 최소 2개는 가짐
				- 각 노드의 최소 key 수(root 제외) = $\operatorname*{ceil}(M/2)-1$
			- internal 노드의 key 수가 x개라면 자녀 노드의 수는 언제나 x+1
			- balanced tree : 모든 leaf 노드는 같은 level에 있게 됨
			- key는 오름차순으로 저장
			- e.g. key = (k1, k2)라고 하면 ? < k1, k1 < ? < k2, k2 < ?로 자식 노드를 나눔
		- B-tree의 데이터 삽입
			- 추가는 조회를 한 후에 leaf 노드에 한다
			- 노드가 넘치면 median key를 기준으로 좌우 key들을 분할하고 가운데 key를 상위 노드로 승진시킨다
		- B-tree의 데이터 삭제
			- 삭제도 leaf 노드에서 발생함
				- internal 노드나 루트 노드의 데이터를 삭제하려고 하는 경우에는 predecessor나 successor와 위치를 바꾼 후 삭제를 진행 (그래야 B-Tree의 성질이 깨지지 않음)
					- predecessor : 나보다 작은 데이터 중 가장 큰 데이터
					- successor : 나보다 큰 데이터 중 가장 작은 데이터
			- 삭제 후 최소 key 수보다 적어졌다면 재조정한다
				- key 수의 여유가 있는 형제 노드(왼쪽, 오른쪽 순으로)의 지원을 받는다
					- 왼쪽이라면 가장 큰 key를 위로 올리고 부모 노드의 key를 내린다
					- 오른쪽이라면 가장 작은 key를 위로 올리고 부모 노드의 key를 내린다
				- 형제 노드 지원이 불가능하다면 부모의 지원을 받은 후 형제와 합친다
					- 왼쪽 또는 오른쪽 노드와 자신 사이의 key를 부모로부터 받고 그 key를 왼쪽 또는 자신에게 합치고 자신 또는 오른쪽 노드를 삭제한다
				- 부모의 지원을 받아 부모 노드에 key 수가 최소 보다 작아지면 부모 노드에서 재조정을 실시한다
					- 부모 노드가 root 노드가 아니라면 1번부터 재조정을 시작
					- 부모 노드가 root 노드이면서 비어있다면 부모 노드 삭제
		- B-Tree는 데이터의 조회, 삽입, 삭제가 모두 O(logN)
		- balanced BST 계열도 O(logN)인데 Index로 B-Tree를 쓰는 이유
			- DB는 secondary storage에 저장되는데 secondary storage는 접근 속도가 느리고 block 단위로 데이터를 읽고 쓰기 때문에 연관된 데이터를 모아서 저장하는게 더 좋음
				- B-Tree가 BST 보다 자녀 노드가 많기 때문에 depth가 얉음 -> 접근 횟수가 적다
				- B-Tree는 block 단위로 데이터를 읽어 올 때 인접한 key를 가져오게 됨
	- hash index 기반의 index
		- hash table이 가득 찼을 때 rehashing을 해야되는데 overhead가 큰 편임
		- equality에 대한 비교만 가능하고, range에 대한 비교가 불가능함
		- multicolumn index의 경우, multicolumn 전체에 대한 attribute(s)로만 검색이 가능함
	- index에 대한 저장 공간도 필요하고, table에 변경이 생기면 index도 변경해줘야 되기 때문에 잘 사용하는 것이 중요함
	- covering index : 조회하는 attribute(s)를 index가 모두 cover할 때 ptr를 통해 추가적인 table 접근이 필요없는 경우

``` MySQL
SELECT * FROM player WHERE name = 'sonny' and team_id = 105;

CREATE INDEX player_name_idx ON player(name);
CREATE UNIQUE INDEX team_id_backnumber_idx ON player(team_id, backnumber);

CREATE TABLE player (
	id INT PRIMARY KEY,
	name VARCHAR(20) NOT NULL,
	team_id INT,
	backnubmer INT,
	INDEX player_name_idx(name),
	UNIQUE INDEX team_id_backnumber_idx(team_id, backnumber)
);

SHOW INDEX FROM player;
EXPLAIN SELECT * FROM player WHERE backnumber = 7;
```

# Partitioning과 Sharding

- partitioning : table을 더 작은 table로 나누는 것
	- vertical partitioning : column을 기준으로 table을 나누는 것 e.g. normalization
		- vertical partitioning이 필요한 이유
			- 실제 table에서 특정 attributes만 select해오는 경우에도, 실제 ssd나 hdd에 저장된 전체 tuple을 가져온 다음에 특정 attribute만 필터링되어서 select되는 것이기 때문에 value의 크기가 큰 attribute의 경우 IO 부담이 큼
			- 자주 사용되는 attribute(s)가 있는 경우
	- horizontal partitioning : row를 기준으로 table을 나누는 것
		- hash-based horizontal partitioning : 특정 attribute를 partition key로 사용해서 hash function을 통과시켜서 나온 index의 hash table에 정보를 저장 또는 접근하는 방식
			- partition key 외의 attribute를 통해 select를 하는 경우에는 full scan해야 됨
- sharding
	- horizontal partitioning이랑 비슷한데 각 partition을 서로 다른 DB서버에 저장함 -> load 분산이 가능함
	- sharding에서 partition key를 shard key라고 하고 각 partition을 shard라고 함
- replication : 주 DB 서버(=master, primary, leader)의 데이터를 동일하게 유지하는 보조 DB 서버(=slave, secondary, replica)를 두는 방법
	- high availability 제공 가능 : primary server에 문제가 발생했을 때 secondary server를 사용할 수 있음
	- read 요청을 secondary server로 분산할 수 있음

# NoSQL Data Model

- RDB의 단점
	- 새로운 column 추가 시 부담이 큼
	- JOIN을 많이 해야되는 경우에 부담이 큼
	- scale-out(추가적인 서버를 증설)을 통한 성능 향상에 제약이 있음 -> scale-up(더 좋은 성능의 하드웨어 사용)을 통해 성능을 키워야 함
- NoSQL
	- flexible schema : 원하는 형태의 데이터를 동일한 table에 넣어줄 수 있음
		- schema 관리를 application level에서 하게 됨
	- 중복 허용 : join을 회피해서 성능 향상
	- scale-out을 통한 성능 향상이 RDBMS보다 쉬움
	- 성능이 좋음 : high-throughput, low-latency
	- e.g. Redis : in-memory key-value database, 주로 DB 앞 단에서 cache로 사용
